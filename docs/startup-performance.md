# Startup performance

> **Scope:** What keeps the Android app fast to open: the launch animation that ends when loading ends, deferred start-up work, R8 + resource shrinking, the baseline profile, pre-paint theme script, latin-only fonts, cached Intl formatters, lazy catalogue, tree-shaking.
>
> **Read when:** you change fonts, `index.html`, `formatters.ts` or what is bundled into the Android build.
>
> **Related:** web-preview.md, data-off-catalogue.md, launch-intro.md, ../android/BUILD_APK.md

What the Android app does to open quickly: the HTML carries a tiny pre-paint script that applies the saved Lite Dark / Dark theme and background before any CSS or React runs (no light flash); fonts are declared in `src/index.css` as two latin-only woff2 faces instead of the fontsource stylesheets (−69 KB of inlined base64; other scripts fall back to the system font); `Intl` number/date formatters are created once per locale + options in `src/utils/formatters.ts` (`numberFormatter`, `dateFormatter`) instead of on every call, and the Today calendar computes its weekday labels only while it is open. The 12 MB food catalogue is not part of that bundle: it is fetched lazily (about 150 ms) the first time a food search opens, so it costs nothing at launch. The tour, widget gallery and demo data are tree-shaken out of the Android bundle by the `VITE_ANDROID_RELEASE` guard in `App.tsx`. Measured in headless Chromium with 4× CPU throttling (median of 5): first paint 304 → 272 ms, app ready 628 → 555 ms, first contentful paint 744 → 656 ms.

## Second round: launch animation, deferred work, R8, baseline profile

**1. The launch animation is a loading indicator, not a fixed delay (biggest win).** Before, the intro overlay always ran its whole timeline (1.06-1.28 s) + a 220 ms hold + a 240 ms fade, about **1.5-1.8 s of overlay on every start**, however fast the app was. Now `useAppReady()` (`src/components/intro/useAppReady.ts`) turns true when the first screen is committed, `document.fonts.ready` has resolved and two frames have painted; `IntroSplash` then interrupts the animation wherever it is and fades out in 140 ms. The animation's own length is only the upper limit, and a tap still skips it. Measured in headless Chromium (desktop CPU, `?view=app`): overlay on screen **about 200 ms instead of about 1.6 s** (3 runs: 205 / 203 / 200 ms). On a slow phone the animation plays for as long as the app really needs to load. Details: [launch-intro.md](launch-intro.md).

**2. Start-up work moved out of the first frames** (`whenIdle()` in `src/utils/idle.ts`, a `requestIdleCallback` wrapper with a deadline). Deferred: `JournalDevice.publishNutrition` (serialises the recent day logs for the widgets), `syncLaunchBackground` (only matters for the *next* cold start), and the notification reschedule (still debounced 400 ms, then idle, deadline 4 s). Natively, `LaunchBackground.applySplashThemeWhenIdle()` replaces the `getIdentifier` lookup + `setSplashScreenTheme` that ran inside `MainActivity.onCreate()` (also next-start only) with a one-shot `MessageQueue.IdleHandler`. The theme attributes, window/WebView background and the pre-paint script stay synchronous (they prevent flashes).

**3. R8 and resource shrinking** (`android/app/build.gradle` release type: `minifyEnabled true`, `shrinkResources true`, `proguard-android-optimize.txt`; rules in `android/app/proguard-rules.pro`). Capacitor ships consumer rules for `@CapacitorPlugin` classes; the app's plugin, widget receivers and `MainActivity` are kept explicitly. **Resources looked up by name must be listed in `android/app/src/main/res/raw/keep.xml`** (the 48 `Splash_<hex>` styles used by `LaunchBackground`, `ic_stat_kak` and `ic_notification_large` used by the notification plugin) or the shrinker deletes them. If you add another `getIdentifier(...)` lookup, add it there too. For Play, upload an **Android App Bundle** (smaller download, less code to load).

**4. Baseline profile (hand-written).** `android/app/src/main/baseline-prof.txt` lists the app, Capacitor bridge/plugin, splash-screen and WebView-helper classes that run on every cold start; AGP packs it into release builds and the new `androidx.profileinstaller` dependency installs it on first launch (also for sideloaded APKs). It is a **starting point, not a measurement**: Google quotes about 30 % faster code execution from the first launch (one third-party write-up 30-40 % cold start; secondary source, treat as a rough estimate), but this app is mostly a WebView, so the gain applies to the Java/Capacitor part of start-up only, not to JavaScript parsing. *Generate a measured baseline profile:* in Android Studio, **File > New > Module > Baseline Profile Generator**, target module `app`, run the generated `BaselineProfileGenerator` on a device/emulator (API 28+, rooted or userdebug image) and let it write `app/src/main/generated/baselineProfiles/baseline-prof.txt`; remove or keep the hand-written file next to it (AGP merges both).

**Considered and not applicable here.** *App Startup library:* the app has no `Application` subclass and no SDK content providers (the only provider is `FileProvider`, which is cheap and needed for backups), so there is nothing to consolidate; do not add an SDK that registers its own provider without using `androidx.startup`. *Analytics / ads / crash reporting / DI:* none exist. *Official splash screen:* already used (Android 12+ system launch screen, colour-matched `Splash_<hex>` themes, no `setKeepOnScreenCondition` hold). *Startup assets:* the 12 MB food catalogue is lazy (see above); no images load at launch (the launch art is inline SVG).

**Known limit:** the web bundle is one inlined 1 MB `index.html` (`vite-plugin-singlefile`), so code-splitting cannot reduce parse time; the WebView must parse it before React mounts. Moving to an external hashed script (V8 code cache) would be the next experiment but changes the single-file delivery of the PWA and Android bundle, so it was not done.
